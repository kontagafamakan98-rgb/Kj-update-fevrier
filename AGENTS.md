## Déploiement & hébergement

- Backend migré de Render (payant) vers Fly.io : `backend/Dockerfile` + `backend/fly.toml`, guide complet dans `backend/DEPLOY_FLYIO.md`. Le frontend reste sur Vercel ; sa variable `VITE_API_URL` doit être basculée vers la nouvelle URL du backend.
- Quirk Fly.io : les health checks envoient un Host (souvent une IP interne) que le TrustedHostMiddleware rejette → 400 en boucle → déploiement échoué. Le motif `TRUSTED_HOSTS=*.internal` ne suffit PAS ; correctif fiable : secret `DISABLE_TRUSTED_HOST_MIDDLEWARE=true`.
- `fly launch` régénère `fly.toml` et écrase les entrées `[env]` ajoutées à la main — revérifier `BACKEND_PUBLIC_URL`/`TRUSTED_HOSTS` après chaque `fly launch`.
- Machines Fly en trial : arrêtées après 5 min tant qu'aucune carte bancaire n'est ajoutée au compte.
- Utilisateurs en Afrique de l'Ouest → héberger en Europe (Francfort, ~100 ms depuis Dakar), pas au Canada. La liste d'IP autorisées MongoDB Atlas doit inclure l'IP de sortie de chaque hébergeur (celle de Render était whitelistée, pas celle de Fly).

## Environnement & configuration

- `BACKEND_PUBLIC_URL` est OBLIGATOIRE hors Render : elle alimente à la fois la liste d'hôtes de confiance (TrustedHost) ET les URLs de callback IPN PayDunya (`build_payment_callback_url`/`build_disburse_callback_url`).

- TrustedHostMiddleware activé par défaut ; le `.env` local de `backend/` pose `DISABLE_TRUSTED_HOST_MIDDLEWARE=true`, donc le local ne teste jamais les contrôles de Host actifs en prod.
- La construction d'URL backend du frontend est CENTRALISÉE dans `frontend/src/utils/backendUrl.js` (`buildApiUrl`/`buildBackendUrl`) : `api.js` et `jobProposalWorkflow.js` l'importent — ne jamais réimplémenter la dérivation de base ailleurs (bug historique `/api/api`). Ordre de priorité des sources : `window.__KOJO_API_URL__`/`__API_URL__` → `VITE_API_URL`/`VITE_API_BASE_URL`/`VITE_BACKEND_URL` → `REACT_APP_BACKEND_URL`/`REACT_APP_API_URL` → localhost:8000 (dev) → `https://api.kojoforafrica.cc.cd`. `photo_url` est toujours une URL Cloudinary absolue (les branches relatives de ces helpers ne servent qu'aux données legacy).
- Géolocalisation : `frontend/src/services/geolocationService.js` est le SEUL module (fusion de `preciseGeolocationService.js`, supprimé). L'ancien `geolocationService.js` avait une classe `GeolocationService` et des bases de villes inline ENTIÈREMENT mortes (aucun consommateur n'importait son default ; les champs `color`/`majorCities`/`timeZone`/`internetPenetration` de son `COUNTRIES` n'étaient lus nulle part). Ne pas recréer de bases de villes côté frontend : la source de vérité est la base backend servie par `/api/geolocation/cities` (cache localStorage 7 j).

- `PUT /users/profile` `profile_photo` n'accepte que des URLs `https://res.cloudinary.com/` (anti-pisteur) ; une chaîne vide est un no-op (avant : 400 latent car `''` ne commençait pas par http/https).

## Architecture & pièges métier

- Collection `db.proposals` est MORTE : la vraie collection est `job_proposals`. Les index de boot (`create_database_indexes`) visaient `proposals` (jamais utilisée) — les index de propositions doivent cibler `job_proposals`.
- Verrou anti double-retrait parrainage (`referral_withdrawal_in_progress`) : seul `kojo_shared.apply_referral_payout_confirmed` le libère (point unique de vérité solde + verrou). Une copie dupliquée dans `kojo_routers_payments` ne le libérait pas (bug bloquant) — ne jamais réintroduire de 2e copie ; le chemin succès de `withdraw_referral_rewards` doit appeler la version de `kojo_shared`.
- `get_current_user` reconstruit `User(**doc)` : un doc legacy invalide (ex. téléphone sans `+`) levait une ValidationError → 500 sur TOUS les endpoints authentifiés. Désormais 401 « contactez le support » — corriger la donnée en base, pas le code.
- `serialize_payment_record` retire les payloads fournisseurs bruts (`provider_confirm_payload`, `disburse_token`, `disburse_provider_response`, `disburse_verified_payload`, `disburse_callback_payload`, `disburse_error`, `provider_response_text`) des réponses API — ne pas les réexposer ; `disburse_token` reste stocké en base et sert à l'IPN disburse.
- La vue PUBLIQUE des jobs (découverte anonyme, `GET /jobs` et `GET /jobs/{id}`) passe par l'ALLOWLIST stricte `JobPublic` (kojo_models.py), jamais par un denylist ni par le document brut : tout champ ajouté au doc Mongo reste privé par défaut (extra='ignore' Pydantic v2), y compris `geo` et `location.latitude/longitude/coordinates` (coordonnées GPS jamais exposées publiquement). La vue CONNECTÉE, elle, renvoie toujours le doc brut sans `_id` — le frontend lit `created_at` en fallback d'affichage (`job.posted_at || job.created_at`) et la liste publique écarte (avec warning) une fiche legacy qui ne valide pas `JobPublic` ; corriger la donnée en base, pas le code.
- `kojo_shared.py` importe `pywebpush` au niveau module malgré `WEBPUSH_AVAILABLE` (find_spec) : avant, un paquet absent crashait tout le boot. L'import est maintenant dans un try/except — conserver ce garde-fou.

## Frontend

- Le proxy `createResourceApi` d'`api.js` génère des URLs qui ne correspondent PAS aux vraies routes backend pour la plupart des ressources. Seuls les proxies `users`/`workers`/`proposals` sont réellement utilisés (les autres — commissions/admin/wallet/search/stats/dashboard/settings — étaient morts, supprimés). Préférer des objets API explicites (`paymentAPI`, `reviewAPI`, `supportAPI`…).
- `handleUnauthorized` (api.js) doit purger localStorage ET sessionStorage : `getAuthToken` lit les deux buckets, donc un token stocké en sessionStorage survivait au 401 (boucle de redirection).
- Les plugins du build vivent dans `frontend/vite-plugins/` (un module par plugin, chacun exportant une fabrique) ; `vite.config.js` ne fait plus que COMPOSER et importer les données (`page-meta`, `page-sections`, `og-cards`, `countries`). Une nouvelle étape de build va donc dans son module, importable par un test, jamais dans `vite.config.js`. Preuve d'invariance : les coquilles pré-rendues sont identiques octet pour octet avant/après une extraction.
- Le chrome des coquilles pré-rendues (`.App`, `.min-h-screen`, la navbar, `main.flex-1`) est publié UNE fois, dans `vite-plugins/prerender/app-chrome.js` : ces conteneurs ne sont pas décoratifs : la navbar fait 65 px et `main.flex-1` se partage la hauteur restante ; une coquille qui les omet publie une autre géométrie que la page qu'elle pré-rend, et Chrome ré-élit alors un élément LCP à la peinture de React. (Le décalage mesuré ci-dessous venait de l'alignement HÉRITÉ de `.App` — retiré depuis, refonte du 25/09/2026 : la puce suivante. Ce qui reste vrai est la STRUCTURE : hauteur de navbar et `main.flex-1`.) Mesuré sur /jobs (Chrome 152, 1350×940) : la 2e ligne du paragraphe d'intro passait de x=67.000 à x=218.578 et l'aire LCP du MÊME texte de 36 002 à 36 049 px² (+0,13 %), pour un `elementRenderDelay` de 1156 à 2345 ms et un score desktop de 92 au lieu de 100. Ne recopiez pas ces conteneurs dans une coquille.
- Le centre de notifications est monté UNE fois pour tout le site : `<NotificationPanel />` dans `src/App.js`, à côté de la navbar. La barre de navigation, elle, ne rend que des DÉCLENCHEURS (`NotificationBell.js`) — UN PAR BARRE, et le partage a changé le 25/09/2026 : la barre du HAUT ne garde sa cloche que dans sa disposition desktop (`hidden md:flex`), et sur mobile c'est la barre de navigation BASSE (`MobileBottomNav.js`, `data-mobile-bottom-nav`) qui la porte comme cinquième item — celle qui est sous le pouce. La disposition MOBILE de la barre du haut n'en a donc plus du tout : deux cloches affichées à la fois feraient deux points d'entrée pour un seul panneau, et c'est la barre de navigation du bas qui est le lieu de la navigation sur un téléphone. Une cloche est un DÉCLENCHEUR sans état, qui transmet son conteneur (`ancre`) au `NotificationContext`, et c'est dans ce conteneur que le panneau se rend par portail React. Il n'en existe donc jamais deux, et il s'affiche SUR la barre qui l'a ouvert sans mesurer un pixel (le conteneur est `relative`, le panneau garde son `absolute right-0`) — le CÔTÉ, lui, est DÉCLARÉ par la cloche (`sens`, propriétaire unique : `notificationPanelPlacement.js`) : vers le BAS sous la barre du haut, vers le HAUT au-dessus de la barre du bas, parce que sous une barre collée au bas de l'écran (`fixed bottom-0`) un panneau qui descendrait sortirait de la fenêtre. Mesuré sur le bundle (Chromium, 412×823, 25/09/2026) : cloche de la barre du bas à `y=744`, panneau 340×258 dont le BAS est à 736 — soit exactement le HAUT de la cloche moins les 8 px de `mb-2` — et son bord droit à 1 px de celui de la cloche (arrondi). Corollaire de mise en page : la grille de la barre basse passe à cinq colonnes quand la cloche est là (`grid-cols-5` pour un connecté, `grid-cols-4` pour un visiteur, les deux classes écrites en clair) — et cinq colonnes sur 412 px font des cases de 74,9 px, donc « Tableau de bord » tient sur DEUX lignes et la barre passe de 80 à 88 px de haut (mesuré : items 72 px, `Tableau de bord` et `Notifications` sans débordement horizontal, `scrollWidth === clientWidth`). Ajouter l'item sans élargir la grille aurait fait passer la cloche sur une SECONDE ligne : c'est ce que le cas jsdom refuse (`grille.className` doit contenir `grid-cols-5`), et la mutation rejouée le dit aussi (`grid-cols-4` → le cas rougit). La barre plus haute reste SOUS le contenu : `main` porte `pb-24` (96 px) pour une barre de 88 px. TROISIÈME MUTATION rejouée, celle du sens : cloche de la barre basse laissée sur le défaut (ouverture vers le bas) → le parcours mobile rougit sur la relation des deux boîtes (« Expected: <= 743.5, Received: 929.09 » : le panneau sort par le bas de la fenêtre), puis restauration à l'empreinte SHA-1. Un écart assumé, écrit ici plutôt que redécouvert : la barre du bas ne se rend pas sur quatre chemins d'authentification (`HIDDEN_PATHS` de `MobileBottomNav.js` : /login, /register, /forgot-password, /email-verification), donc un utilisateur CONNECTÉ qui ouvrirait l'un d'eux sur un téléphone n'a plus de cloche du tout — le header mobile n'en porte plus et la barre du pouce est absente. C'est le prix du choix « un seul point d'entrée affiché par barre » : l'autre option (garder la cloche du header ET celle du bas) affiche deux cloches à la fois sur toutes les autres pages. C'est le NOMBRE de panneaux qui était le défaut : avec un panneau par barre, chacun écoutait `mousedown` sur le document, et l'instance dont le conteneur était `display:none` ne reconnaissait pas l'appui fait dans l'autre comme « intérieur » — elle appelait `closePanel()`, le panneau se démontait PENDANT l'appui, et le `click` qui suit n'atteignait plus le bouton : supprimer une notification ou « tout marquer comme lu » ne partait JAMAIS, sans requête et sans message (symptôme rapporté : « la notification montre toujours 1 et refuse de disparaître »). Deux règles en découlent, et deux seulement : (1) un appui est « dedans » quand il tombe dans l'`ancre` — le panneau ET la cloche qui l'a ouvert, les deux seuls endroits qui ne doivent pas fermer ; l'appui sur la cloche doit être ignoré au `mousedown`, sinon le `click` qui suit ROUVRIRAIT le panneau que l'utilisateur vient de fermer ; (2) le panneau se ferme si son `ancre` cesse d'être affichée (`getClientRects().length === 0`), parce qu'une rotation ou un redimensionnement franchit le point de rupture `md` (768 px) et laisserait sinon un panneau `isOpen` dans un conteneur invisible — la cloche redevenue visible semblerait ne rien faire, son premier appui ne faisant que refermer un panneau que personne ne voit. Un test qui n'envoie qu'un `click` isolé ne peut pas voir le défaut d'origine (le navigateur envoie `mousedown` PUIS `click`) : la séquence réelle est rejouée par `src/components/__tests__/NotificationCenter.test.jsx` (19 cas, dont « un seul panneau pour deux cloches », l'hébergement par la barre qui a ouvert, la grille à cinq colonnes de la barre du bas et le sens d'ouverture déclaré dans les deux sens) et par `e2e/notifications.spec.js` dans un vrai Chromium (qui mesure aussi le franchissement de 768 px, invisible en jsdom qui ne calcule aucune mise en page). Le troisième parcours de ce fichier est MOBILE (412×823, `hasTouch`, `isMobile`) : les deux barres vivant dans le même DOM, « laquelle gagne » n'est pas une évidence mais une propriété à mesurer, et elle se lit sur l'hébergement — le panneau est porté par la cloche AFFICHÉE (`combien: 1, affichees: 1`). SÉQUENCE TACTILE MESURÉE (sonde du 25/09/2026, journal des événements du document) : un `tap()` produit `pointerdown → touchstart → touchend → mousedown → mouseup → click`. Ce n'est pas un détail de curiosité : le panneau se ferme sur `mousedown` et supprime sur `click`, donc au doigt les DEUX mécanismes s'exécutent, dans cet ordre — si le `mousedown` de compatibilité était pris pour un appui extérieur, le panneau se fermerait puis le `click` appellerait `togglePanel` sur un panneau déjà fermé et le ROUVRIRAIT : il semblerait insensible au doigt. Le parcours tient cinq propriétés qui n'existent qu'à cette taille : l'hébergement par la cloche affichée (ET par la barre du BAS, vérifié explicitement dans `[data-mobile-bottom-nav]` — `{ combien: 1, affichees: 1 }` ne dit pas LAQUELLE des deux barres est affichée), le bord DROIT du panneau qui coïncide avec celui de cette cloche ET son BAS qui touche le HAUT de cette cloche (l'ancrage est du CSS, aucune coordonnée n'est écrite en dur — l'assertion survit à un changement de padding ou de largeur de barre), le panneau entier dans 412 px (et pas non plus par le HAUT : c'est la seule direction qui lui reste), la croix atteignable SANS SURVOL et ≥ 44 px, et un appui EXTÉRIEUR qui atteint sa CIBLE (un AUTRE item de la barre du bas, à quelques pixels de la cloche : le panneau se ferme ET l'écran change de route). Piège d'outillage mesuré au passage : `page.touchscreen.tap(x, y)` sur des coordonnées calculées est fragile sur cet hôte — un `mousedown` est arrivé sur un `DIV` pendant un re-rendu, panneau jamais ouvert — alors que `locator.tap()` produit la MÊME séquence d'événements de façon fiable. Preuves d'échec rejouées le 25/09/2026 : appui sur la cloche traité comme extérieur → rouge sur l'inversion (`Expected: 0, Received: 1`) ; fermeture extérieure neutralisée → rouge sur le logo ; surface captante `fixed inset-0 z-10` remise dans le portail → Playwright signale « intercepts pointer events » et le parcours échoue ; restauration vérifiée à l'empreinte SHA-1 d'origine. Preuve d'échec du garde d'ancrage, rejouée le 25/09/2026 : le retirer fait rougir le cas jsdom ET le parcours navigateur (`toHaveCount(0)` → `Received: 1`, le panneau restant dans la barre masquée), puis restauration à l'empreinte SHA-1 d'origine. Ce garde n'est PAS dans `.github/scripts/guard-proofs.json` : ce registre classe les scripts qui AUDITENT le dépôt et sortent en 1 sur un écart, et n'a jamais porté de chemin `src/` — y déclarer un composant React serait un classement faux.
- Une surface qui se ferme sur un appui EXTÉRIEUR ne doit pas AVALER cet appui. Deux formes coexistaient dans le dépôt : un écouteur `mousedown`/`touchstart` sur `document` qui demande si l'appui est tombé dans son propre conteneur (`contains`) — l'appui poursuit vers sa cible et le menu se referme par effet de bord, comme le ferait un menu natif du navigateur — et une surface PLEIN ÉCRAN (`fixed inset-0`) posée pour le capter, qui devient elle-même la cible et fait perdre le clic. MESURÉ (Chromium, 25/09/2026, `e2e/appuis-exterieurs.spec.js`) : tant que le menu de langue était ouvert, Playwright retentait 55 fois le clic sur le lien « Emplois » de la MÊME barre, chaque fois arrêté par `<div class="fixed inset-0 z-10">` — le premier appui sur n'importe quelle commande de la barre (lien, cloche de notifications, déconnexion) était perdu. C'est le même défaut de fond que le panneau de notifications dupliqué, par un autre chemin : un appui visant une commande n'atteint pas cette commande. Les deux surfaces captantes (le menu de langue, dans la barre ; le sélecteur de pays de /jobs) sont remplacées par l'écouteur. Un fond VISIBLE (`bg-black/30`, `bg-black/50`) reste légitime : un tiroir ou une modale bloque la page derrière, et c'est alors l'intention — la règle distingue les deux par le FOND, pas par une liste d'exceptions à tenir à jour. Deux conséquences à ne pas reperdre : l'appui sur le DÉCLENCHEUR ne doit pas fermer (sinon le `click` qui suit ROUVRE le menu), et un écouteur extérieur ne s'enregistre QUE tant qu'il a quelque chose à fermer (`CountrySelect` le posait à chaque montage, pour ne jamais rien fermer sur /register et /profile). Garde : `src/components/__tests__/appuis-exterieurs.test.jsx` — comportement des trois composants (séquence réelle `mousedown` → `click`, appui sur une autre commande) ET forme du motif sur tout `src/` (aucune surface plein écran sans fond, aucun écouteur sans `contains`), chacune avec des cas synthétiques qui prouvent qu'elle sait mordre, et un décompte qui prouve que le balayage a lu son sujet. Il vit avec ses preuves, comme `antiClsSkeletons.test.jsx`, et non dans `frontend/scripts/` : ce dossier est réservé aux scripts qui AUDITENT le dépôt et sortent en 1 sur un écart. Preuve navigateur : `e2e/appuis-exterieurs.spec.js` (3 parcours). Mutation rejouée le 25/09/2026 : remettre la surface captante fait rougir 2 cas jsdom (dont le balayage, qui nomme le fichier et la ligne) et 2 parcours navigateur, puis restauration vérifiée à l'empreinte SHA-1 d'origine. jsdom ne peut pas voir ce défaut (aucune mise en page, et `fireEvent.click` envoie l'appui directement à l'élément) — d'où les deux plans.
- Le LCP d'une page pré-rendue se gagne sur une ÉGALITÉ de géométrie entre les deux peintures : la coquille peint avant le JavaScript, `createRoot()` efface `#root`, et React reconstruit le même élément. Un remplacement de MÊME TAILLE n'enregistre aucun nouvel élément LCP ; un remplacement PLUS GRAND en enregistre un second, plus tardif, et toute la chaîne JavaScript entre alors dans le graphe LCP simulé de Lantern (mesuré sur /jobs : `elementRenderDelay` de 1156 à 2345 ms, score desktop 92 au lieu de 100). La géométrie de l'élément LCP a donc UN propriétaire dans `src/config/page-sections.js`, lu par les deux canaux : `heroTitleClass`/`heroSubtitleClass` pour l'accueil, `frameClass`/`titleClass`/`introClass`/`noteClass` pour /contact. Deux gardes mesurent la règle — `scripts/__tests__/check-home-hero-lcp.test.js` (héros + amorçage après le premier paint) et `scripts/__tests__/check-contact-lcp.test.js` (introduction de /contact) — et `e2e/contact-lcp.spec.js` mesure le FAIT en navigateur : une seule candidate LCP, horodatée au premier paint. Piège des sondes locales : leur critère `/MAIN/` date d'avant le chrome, où le corps de la coquille vivait HORS de `main` ; depuis, il est dedans, donc une candidate de la coquille est annoncée « REACT » à tort — trancher sur la chronologie des candidates, jamais sur ce critère. La règle est mesurée sur TOUTES les routes pré-rendues par `e2e/lcp-geometrie.spec.js`, à 412×823 et 1350×940 : la liste vient de `src/config/page-meta.js` (jamais recopiée), chaque route est chargée DEUX fois — une fois avec le bundle d'entrée bloqué par `page.route` pour mesurer la coquille SEULE, une fois normalement — et le test échoue si la navigation réelle enregistre plus d'une candidate LCP, si elle n'est plus horodatée au premier paint, ou si l'aire peinte par React dépasse celle de la coquille (tolérance 1 px²). Relevé du 25/09/2026 : 22/22 vertes, aires identiques de part et d'autre. Une page pré-rendue ajoutée à la table est donc mesurée sans qu'on l'y inscrive.
- LE CONTENU d'une coquille pré-rendue se juge MOT POUR MOT face à React, DANS LA PAGE et non dans le HTML (sonde du 25/09/2026 : `e2e/texte-coquille-react.spec.js`, 22 cas = 11 routes × 2 tailles ; harnais `e2e/helpers/texte-coquille.js`). Le trou qu'elle ferme : les deux sondes de géométrie COMPTAIENT les divergences de contenu sans les juger (« divergence de CONTENU, couverte par le garde de provenance ») en déléguant à `scripts/check-shell-text-provenance.js` — un garde qui lit le HTML du build, donc une CHAÎNE, pas une peinture. Une coquille peut ainsi publier « 1. Email » là où React peint « 1. » puis « Email », ou « 💬 » là où React peint une icône lucide, sans que rien ne rougisse. La règle, mesurée sur les deux peintures (bundle d'entrée bloqué d'un côté, premier rendu de React de l'autre) : tout texte VERBAL peint par la coquille doit se retrouver, phrase ENTIÈRE (jamais un mot isolé — tout mot est contenu dans une phrase), dans la même BANDE verticale (recouvrement > 50 % de la plus petite hauteur) ET la même ZONE (`main` ou chrome), ce qui rend la sonde indifférente au DÉCOUPAGE du DOM : « 1. Email » d'un côté et « 1. » + « Email » de l'autre sont la même phrase dans la même bande, « 1. Courriel » ne l'est pas ; et tout GLYPHE publié (emoji, puce, flèche) doit avoir un pendant peint par React dans la même bande — texte IDENTIQUE si React en peint un là, SVG ou image sinon (mesuré : les 4 drapeaux de `/` sont 4 `<svg>` chez React, les 6 icônes de /support 6 icônes lucide, et les emojis des autres pages sont publiés en TEXTE des deux côtés). Relevé : **0 manquant sur les 10 routes comparables** (`/payment` redirige vers /login : NOMMÉE dans le journal, jamais comptée comme un vert), sauf les deux chiffres de `/` — la page lit `/public/stats` et formate par `toLocaleString()` (« 1+ » avec la fixture) quand la coquille publie les replis statiques déclarés dans `src/config/page-sections.js` (`stats[].shellText`, « 1 000+ »). Ces deux écarts sont DÉCLARÉS avec leur raison ET avec une CONTREPARTIE vérifiée (React doit peindre un nombre suffixé dans la bande : la preuve que l'écart reste « une donnée contre un repli », pas « un texte disparu »), et un écart déclaré qui n'est plus utilisé ou dont la contrepartie a disparu fait ROUGIR — une exception qu'on n'ose plus retirer est une exception qui mente. Le CHROME se compare dans l'ORDRE des mots, PAS dans la bande, et c'est une décision mesurée : la hauteur du pied de page est une fonction de celle du CORPS, que React change avec du contenu asynchrone — sur /jobs la liste des missions emporte le pied de page de y≈699 à plus de 1 800 px et la bande de la coquille est occupée par la barre de navigation MOBILE de React, donc exiger la bande ferait rougir les 9 textes du pied de page sans qu'un seul mot manque. - Les tests patchent le module où la fonction est UTILISÉE, pas où elle est définie : ex. `kojo_routers_payments.create_paydunya_invoice`, `kojo_routers_users_referral.submit_paydunya_disburse_invoice`, `kojo_shared.notify_user_localized`. - Un test qui découpe un sous-processus Python doit figer l'encodage du tube des DEUX côtés — `env={**os.environ, "PYTHONIOENCODING": "utf-8"}` sur l'enfant ET `encoding="utf-8", errors="replace"` sur le parent (cf. `test_cors_origins.py`, `test_audit_none_signatures.py`). - `pytest -k "Classe::test"` ne sélectionne RIEN et sort en **5** (« aucun test collecté ») : passer l'identifiant de nœud en argument positionnel, et exiger `code == 1` dans un harnais de mutation — sinon une mutation inopérante passe pour un succès.
- Une preuve par mutation qui touche les fichiers RÉELS doit les lire et les écrire en **mode brut** (`open(..., newline="")`) et comparer les empreintes SHA-1 avant/après. Un aller-retour `read_text`/`write_text` convertit LF en CRLF sous Windows, donc « restauré » devient faux sans que `git` le signale : `.gitattributes` (`*.py text eol=lf`) normalise à l'affichage, et `git diff --numstat` rend **0 ligne** pour un fichier dont les octets ont changé. Garder l'ORIGINAL et le MUTÉ dans **deux variables distinctes** : un harnais qui applique la mutation dans la variable qu'il restaure ensuite écrit le texte MUTÉ en croyant restaurer — constaté le 19/09/2026, cinq mutations laissées dans l'arbre alors que le rapport annonçait « identique », et sans l'empreinte SHA-1 de référence aucun moyen de le voir.
- Muter un fichier réel puis le restaurer **sans** `PYTHONDONTWRITEBYTECODE=1` (ou `-B`) laisse un `__pycache__` empoisonné : un `.pyc` reste valide tant que *(mtime tronqué à la seconde, taille)* n'a pas bougé, et remplacer `48` par `24` **ne change pas la taille**. Les sous-processus importent alors le code muté alors que la source est déjà restaurée (constaté le 19/09/2026 : les 4 fichiers à leur SHA-1, et 3 tests rouges sans cause dans l'arbre).

- LES GARDES DE GÉOMÉTRIE ÉTAIENT CALÉS SUR UN HÔTE, ET LA CI LES A DÉMASQUÉS (26/09/2026, PR #152). Le point commun de deux rouges : une grandeur de TEXTE jugée par une constante d'un seul poste. La hauteur d'un bloc de texte suit les POLICES de l'hôte — le nombre de lignes repliées n'est pas connaissable avant la mise en page — et l'aire de son ENCRE suit la largeur de ses glyphes. (1) `e2e/carte-accueil.spec.js` comparait la position du bloc de carte AVANT l'appui — au chargement, quand les neuf sections différées de l'accueil sont mises en page avec les constantes de `src/App.css` — à APRÈS l'appui, quand `click()` a amené le bloc dans la vue et que ces sections se sont POSÉES. Deux mises en page différentes, donc un décalage qui n'est pas celui de l'appui : mesuré sous une police étrangère (Verdana, sonde d'atelier), le bloc bouge de 99,1 px (1350×940) / 135,3 px (412×823) au moment où les sections se posent ; sur le runner Linux de la CI, de 25,5 px (4 316,8 → 4 342,3 px), exactement le chiffre du rouge. Le parcours amène désormais le bloc dans la vue avant de mesurer et PUBLIE la dérive (0,0 px ici, 99,1 px sous Verdana) : le protocole corrigé rend Δ(appui) = 0 px dans les deux cas, ce qui est la propriété qu'il prétend mesurer. Ce qui n'est PAS réparable, et qu'il faut dire : aucune constante CSS ne rend la hauteur réservée exacte sur un autre hôte — c'est le prix du levier `content-visibility`, borné par `style-layout-document` (nœuds + hauteur, plancher 80 %), et le commentaire de `src/App.css` ne prétend plus le contraire (il disait les valeurs « VÉRIFIÉES section par section », ce que cette sonde ne fait pas). (2) `e2e/lcp-geometrie-declaree.spec.js` : l'aire de l'encre de l'élément élu, mesurée sur le runner Linux, vaut jusqu'à −18 % de celle de ce poste (/support desktop 7 616 contre 9 324 px², à BOÎTE d'élément identique — 16 380 px² des deux côtés), et ses planchers étaient calés à 1 à 3 % sous UNE mesure (/forgot-password mobile : 13 000 pour 13 104 mesurés en CI ; /login mobile 2,9 %). Ils valent maintenant ≈ 70 % de la plus petite des QUATRE mesures connues (deux tailles × deux hôtes), les quatre chiffres en commentaire de chaque ligne — et le commentaire dit aussi ce qu'un plancher NE PEUT PAS faire : sans le bloc déclaré (`_sonde-plancher.spec.js`, feuille injectée avant le premier paint) le plus grand texte restant vaut encore 9 025 à 12 285 px², donc c'est l'IDENTITÉ des classes qui tranche, pas l'aire.
